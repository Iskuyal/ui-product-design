# 体验契约

在新流程或改版触及入口、导航、任务状态时读取。把以下契约压缩到本次需要的规模；它是执行记录，不是要求提交一套冗长文档。

## 从完成状态逆推

填写一句：“[用户] 在 [场景] 通过 [动作] 得到 [可见成果]。”成果必须是用户能判断的状态，例如保存了一条记录，而不是“提升体验”。

先画最短任务路径，再记录必要分支。每个页面写一个主要职责，避免入口页同时承担宣传、配置和高密度工作台三个职责。

```text
入口 → 任务开始 → 必要输入/选择 → 结果 → 下一步或返回
                        ↘ 可恢复错误 → 保留输入 → 重试
```

流程图中的名称来自产品，示意图不规定实际页面数量；单页任务可以把这些状态放在同一页。

## 任务覆盖清单

本次有多个主要任务时，记录“任务 → 用户可见成果 → 独有导航/权限/提交语义 → 适用状态 → 验证证据或缺口”。例如订单处理、成员权限与数据导出分别有结果和恢复方式，不能把三个任务都归为一种列表页来抽样验收。

每种不同语义的主要任务至少覆盖一条完整路径及适用高影响分支；同构页面可抽样，记录抽样理由和共享行为依据。切片是第一步，不是最终覆盖范围。仅设计的清单记录稿件/状态说明，不把未运行的任务标为运行通过。

## 动作与路由记录

| 用户动作 | 起点与真实终点 | 前置条件 | 成功反馈 | 失败/取消/返回 |
|---|---|---|---|---|
| 产品实际动作名 | 项目路由或页面路径 | 登录/权限仅在必要时 | 用户看见什么 | 输入、滚动和意图怎样恢复 |

记录哪些是应用内页面、外链、tab、弹层；根据平台选择正确导航。对已有项目先读取真实路由，不凭空编造目标。

着陆页每个 CTA 都应有承诺：点击后得到什么、需不需要账号、是否会丢失当前选择。没有真实后端的原型可以提供演示模式并明确标识；不伪装提交成功。

首次访客和回访用户可走不同入口。已登录用户可以直接进入任务；宣传页作为可返回的介绍，而不是强制广告关卡。分享进入的详情保持上下文，登录或授权取消后有继续浏览的路径。

## 状态只覆盖适用分支

| 情况 | 界面职责 | 验证问题 |
|---|---|---|
| 加载/刷新 | 表达进行中的动作，刷新尽量保留已有内容 | 慢响应时会不会重复提交？ |
| 首次为空 | 解释下一步和所需输入 | 用户能开始任务吗？ |
| 无搜索结果 | 保留查询并提供修改方式 | 是否误当成没有数据？ |
| 错误/离线 | 说明问题、保留输入、给出恢复动作 | 恢复后会不会重复创建？ |
| 权限拒绝/登录取消 | 解释受限能力，提供可用路径 | 是否被困在循环弹窗？ |
| 成功 | 显示实际成果与下一步 | 是否只是一个模糊 toast？ |
| 禁用/提交中 | 原因可理解，避免重复操作 | 用户知道如何恢复可操作状态吗？ |
| 编辑未保存/删除 | 清楚说明影响，按风险提供撤销或确认 | 返回、手势、取消会发生什么？ |

按业务触发状态，不为纯静态内容制造假加载。改版任务需保留现有数据格式、权限边界与副作用；发现既有缺陷时说明对范围的影响。

## 页面与模块内容

先写实际标题、动作和示例结果，再确定容器。一个模块提供一种证据或回答一个问题；重复相同卖点的模块应合并。

每段内容注明来源：真实产品数据、用户提供素材或演示示例。需要尚未存在的能力时，将其标为计划，不把概念图包装成实际产品成果。

可观察的可用性检查：让未看过设计的人解释用途、指出下一步并完成一次任务；记录误解和停顿。没有真实受试者时，只能报告启发式走查。转化、满意度与任务成功率需要真实研究数据，不能从视觉评分推出。
