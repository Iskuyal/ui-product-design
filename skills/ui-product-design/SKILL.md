# UI 产品设计

让视觉表达服务于一个具体产品和一条能完成的任务。大胆来自对题材的判断，质量来自真实内容、完整状态和实际验证。

## 先确定本次工作

读取项目的 AGENTS.md、现有页面、路由、组件、设计资源与运行命令。识别交付模式：

- **新设计**：从任务到视觉方向，再完成所需页面。
- **改版**：列出要改善的问题，保留已验证的功能、路由、数据契约和用户习惯；修改前按 [验证证据](references/verification.md) 的改版基线段记录现状与影响面，再在现有系统中寻找变化空间。
- **仅设计**：交付可审阅方案或原型，明确哪些交互尚未实现。

精确文案替换、低风险样式修补或准确参考稿中的小调整，在任务含义、费用/权限/数据影响和结果承诺保持时，直接定位元素，执行修改、相邻影响和必要渲染检查即可；跳过完整简报、体验契约、随机种子、方向比较与独立评分流程。轻量分支仍核对可见文案及辅助技术名称与真实动作一致。涉及承诺变化时，补充对应动作和结果的核对；例如“取消订阅”不能只改成“关闭提醒”而保留取消付费订阅的行为。发现实质范围歧义再澄清，不因此启动整套创作或整站改版。

Web App 使用 Web 适配；“App”尚不明确且仓库无法识别时，确认是原生、跨端还是移动网页。目标用户、核心任务或品牌约束缺失且会改变设计时，先问关键问题；等待期间可以检查项目、资源和已有证据。对可逆的小选择，公开假设后继续。

用一段简报记录：**谁、什么场景、要完成什么、首个可见成果、目标平台、已有约束、交付范围**。随后给出简短计划，每步带验证。例如“定义入口和完成状态 → 检查主 CTA 的终点；完成页面和状态 → 走通任务；截图评审和修订 → 保存反馈与复查证据”。

完成条件：核心任务可以明确描述；影响架构的歧义已解决；计划与用户授权范围一致。小改动按影响缩小流程，不重新设计整站。

## 1. 先画任务，再画页面

读取 [体验契约](references/experience-contract.md)，形成范围内的主要任务清单、任务路径、页面职责、路由/返回行为和必要状态。明确每个主动作的入口、前置条件、成功结果和失败恢复。

用户要求着陆页时，把“理解产品 → 点击明确的主动作 → 进入对应任务 → 看见成果”连接起来。着陆页不是应用主页的另一个皮肤：首次访客需要理解价值，回访用户需要快捷入口。App 和小程序从分享、二维码、深链进入任务时，保留直接入口；除非任务需要，不强制绕经宣传页。

每个模块回答一个用户问题，承担一种职责：展示成果、解释用法、提供可信证据或促成下一步。场景感由这些职责组织，避免为每个模块另造一个主题。没有真实数据时，使用清晰标识的示例，不能伪造用户数、评价、合作品牌或效果承诺。

完成条件：主 CTA 有实际或明确待实现的目的地；路径覆盖返回和恢复；页面数量由任务决定。

## 2. 建立有理由的创作方向

读取 [创作方向](references/creative-direction.md)。品牌与明确参考优先；自由创作或用户要求时，先用 shell 生成长随机字母数字串：

```powershell
& "<skill目录>/scripts/new-design-seed.ps1" -Length 128
```

上例在当前 PowerShell 中执行；另开进程时选已有的 `pwsh -NoProfile -File` 或 Windows 的 `powershell.exe -NoProfile -File`，后接带引号的脚本路径与长度。两者都不可用时，用环境已有 shell 的随机源实现等价操作，不为生成字符串安装运行时。将字符串只存于内部工作记录，不放入产品文案、页面、可交付前端包或截图。

从字形节奏、重复片段或数字产生主观联想，再通过产品语境筛选。它是发散工具，不是用户研究或自动决定配色的算法。生成方向后固定种子；后续靠判断修订，不靠反复抽签。

比较少量真正不同的方向：构图、内容组织、图形语汇至少一项有实质差异。选择适合任务的一种，并说明舍弃其他方案的理由。已有精确设计要求时直接深化它，不为展示创意重做。

写一个短设计契约：主视觉概念、内容节奏、字体及中文回退、语义色彩、布局规则、展示型页面的记忆点、应删掉的装饰。高频任务页面可以通过信息效率和成熟组件完成适配，不额外强求特色装饰。像素艺术、鲜明图形或空间场景均可使用，但以可读、可操作为底线。

完成条件：内容组织、层级与视觉选择有明确的任务理由；展示型页面形成题材辨识度，高频任务页面保持信息效率与既有设计系统；种子没有进入用户界面。

## 3. 用真实内容落实设计

实现前读取 [平台适配](references/platforms.md) 中目标平台段落；涉及插画、像素艺术或较复杂动效时读取 [图形与动效](references/art-and-motion.md)。仅设计模式将以下要求落在可审阅稿件/原型和状态说明上，不因此新增未经授权的编码、客户端安装或后端接入。

把设计契约转成当前技术栈的语义 tokens 与少量可复用组件：文字层级、表面/正文/动作/状态色、间距、容器、交互状态、图形和动效规则。先复用项目已有资产和合适的平台控件；新增依赖要能说明解决了什么问题。

先完成一条有代表性的纵向切片：入口、任务页面和结果；同时展示它的加载、空、错误或权限分支，再扩展范围内的页面和任务。切片用来暴露风险，不能替代完整范围；导航、权限或提交语义不同的主要任务分别落实。用真实或明确标识的示例内容验证长标题、中文换行、数字、图片比例和内容密度。

布局服从信息优先级。宽屏可以并列比较，窄屏重排任务顺序；触屏可直接操作，不依赖 hover。状态传达同时使用文字或图标；图片不承载唯一的关键信息。文案命名用户的动作和结果，不暴露无助于决策的实现细节。

完成条件按交付模式判断：实现模式按任务清单逐项确认成果，每种不同导航、权限或提交语义的主要任务至少走通一条路径，关键状态可到达且既有行为保持；仅设计模式清单内各任务的路径、状态和控件关系可审阅，并标出未实现的交互。两者都检查视觉与设计 tokens 一致。

## 4. 验证与独立评审

按 [验证证据](references/verification.md) 执行适合本次范围的检查。实现模式捕获实际渲染的主入口、目标任务页、必要状态和至少一个窄屏场景；仅设计模式使用标明身份的稿件/原型画面，不能编造实际运行截图。截图之外，按实际可用环境验证导航、表单、返回、恢复和辅助功能；静态设计只能报告静态证据。

用户要求独立评审，或执行完整新设计/显著改版且环境允许委派时，执行 [评审控制流程](references/review-controller.md)。评审使用该文件指向的固定提示；每轮由新上下文读取当前截图和最小简报。主 agent 负责实际交互与技术检查，评审 agent 负责对可见设计给出独立判断。

依据最重要反馈做定向修改，保持既定方向；删减没有信息作用的装饰也是有效改进。有分歧时核对用户任务、参考和渲染证据，不把“评审喜欢”当成更换产品方向的理由。

完成条件：适用的检查有证据或明确缺口；评审和修改过程可追溯；遵守控制流程的完成与停止条件。没有独立评审能力时明确未完成独立评审，不能用自评替代。

## 交付

交付实际页面/设计文件、简短设计理由、核心流程与状态说明、验证结果及证据位置。说明哪些只是示例、模拟器或静态证据，哪些得到真实交互或真机确认；不把审美评分宣称为用户研究、转化率或上线质量证明。只做用户授权的实现，发布和外部写入仍按本次授权处理。

需要理解方法来源或核对平台规则时，读取 [来源与取舍](references/sources.md)。无需在每次设计时重读全部文献。
